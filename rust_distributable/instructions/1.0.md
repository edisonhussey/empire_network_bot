Sure. The core design we discussed for OpenAutomation is:
- The app is a Rust desktop application with all automation logic and its database stored locally on the user’s machine.
- Use something like SQLite for local data/config/history rather than a remote DB.
- Build cross-platform binaries for Windows, macOS, and Linux.
- Host downloads on something like Cloudflare R2 or GitHub Releases; for a more private/professional setup, use a website plus authenticated, short-lived download links rather than public releases.
- Keep distribution invite-only if you only want trusted users: accounts, invite codes, device limits, and optionally licence revocation.
For licensing, use Ed25519 signatures:
Your machine/server:
PRIVATE KEY → creates/signs licences

Every OpenAutomation binary:
PUBLIC KEY → verifies licences

You generate the Ed25519 keypair once. The private key never goes inside the distributed binary. Every copy of OpenAutomation can contain the same public key.
Each user gets a separate signed licence containing fields such as:
{
  "license_id": "abc123",
  "issued_at": 1790985600,
  "expires_at": 1798761600,
  "tier": "pro",
  "device_limit": 1
}

You sign the exact payload using your private key. The user can read or edit that JSON, but changing anything—such as:
30 days → 1000 days

breaks the signature.
The program effectively does:
read payload
      ↓
verify Ed25519 signature using embedded public key
      ↓
invalid signature → reject
      ↓
valid signature
      ↓
parse JSON into Rust struct
      ↓
check expiry/features/device
      ↓
allow application

So JSON turns into normal Rust values with something like Serde:
struct License {
    license_id: String,
    expires_at: u64,
    tier: String,
}

A licence could conveniently be represented as:
OA1.<base64 payload>.<base64 signature>

When somebody renews, you do not make a new keypair. You simply create a new payload with a later expiry and sign it again with your existing private key:
Old:
expires_at = December 2026

Renewed:
expires_at = December 2027

The same public key inside the application validates both.
For harder reverse engineering, compile Rust with release optimisations, LTO and stripped symbols. You can also place licence checks in several important execution paths rather than having one obvious if license_valid() check. None of this makes a locally running application impossible to crack; a determined reverser can patch machine code. Ed25519 mainly prevents the easy attack of editing licence parameters and manufacturing valid licences.
For networking, use TLS for anything between OpenAutomation and infrastructure you control. Certificate pinning can make casual interception with Burp/Fiddler/Charles harder. However, if OpenAutomation connects directly to Goodgame Empire, you have to use whatever transport/protocol GGE supports—you cannot add your own encryption around that connection without the server understanding it.
And for GGE itself, we discussed using projects like pygge/EmpireCore as references and implementing the equivalent natively in Rust using roughly:
tokio
reqwest
tokio-tungstenite
serde
rusqlite
Tauri (if desired for desktop UI)

with a structure like:
OpenAutomation
├── GGE protocol/client
├── WebSocket/session/heartbeat
├── attack/config/map modules
├── automation scheduler
├── local SQLite storage
├── licence verification
└── desktop UI

The overall goal is therefore: native Rust client, local-only user data, private/invite-only distribution, signed time-limited licences, and enough binary/network hardening that casual users cannot simply copy or modify it.
