Yes — they can edit the JSON file, but that should make the licence invalid immediately.

The key is that you do not trust the JSON by itself. You trust only JSON whose exact contents match a valid Ed25519 signature.

Example licence payload:

{
  "license_id": "abc123",
  "expires_at": 1798761600,
  "tier": "pro"
}

Your server signs the exact serialized bytes of that payload:

payload bytes
    ↓
Ed25519 sign(private_key, payload)
    ↓
signature
You ship something like:

payload:
{"license_id":"abc123","expires_at":1798761600,"tier":"pro"}

signature:
4ab6d9f8...
The Rust program does:

read payload
read signature

verify(public_key, payload, signature)

if verification fails:
    reject licence

if verification succeeds:
    parse payload
    check expires_at
So if the user changes:

"expires_at": 1798761600

to:

"expires_at": 9999999999

the bytes changed.

Therefore:

original payload
    ↓
original signature
    ↓
VALID

modified payload
    ↓
original signature
    ↓
INVALID
They cannot generate the new correct signature because they don't possess your private key.

How JSON becomes internal Rust values
You'd normally deserialize it with Serde:

#[derive(serde::Deserialize)]
struct License {
    license_id: String,
    expires_at: u64,
    tier: String,
}

Then:

let license: License = serde_json::from_slice(payload)?;

Now internally you have:

license.expires_at
license.tier
license.license_id

But importantly, you verify the signature before trusting those fields.

Conceptually:

verify_signature(&payload, &signature)?;

let license: License = serde_json::from_slice(&payload)?;

if now > license.expires_at {
    return Err("Licence expired");
}

Don't do:

let license = parse_json(...);

// use licence first

verify_signature(...);

Verification comes first.

One thing I'd change from plain JSON
JSON has formatting variations:

{"expires_at":123}

versus:

{
    "expires_at": 123
}

They mean the same thing but have different bytes.

The easiest solution is to sign the exact serialized payload and distribute those exact bytes unchanged.

Alternatively, use a deterministic encoding such as canonical CBOR/messagepack, or have a fixed canonical JSON serializer.

For example your licence file could actually be:

OA1.<base64 payload>.<base64 signature>
The app decodes the payload, verifies it, and then parses it.

But there is another attack
A more skilled person doesn't need to change the licence.

They could reverse the binary and find logic equivalent to:

if now < license.expires_at {
    allow_program();
}

and patch it into:

allow_program();

Or patch:

verify_signature(...)

to always return success.

That's the fundamental limitation of software running entirely on someone else's machine.

So Ed25519 protects you very strongly against:

open licence file
change 30 days → 1000 days
save
but it cannot mathematically prevent:

reverse engineer executable
patch licence check out
For your intended audience, though, that's a much bigger barrier.

You can make that harder by having several checks spread through the application instead of one:

startup
    → verify licence

loading automation
    → verify entitlement

scheduler starts
    → verify entitlement

sensitive operation
    → verify entitlement
rather than one obvious:

if license_valid {
    start_everything();
}

There is also a separate issue with time. If everything is fully offline and you use:

SystemTime::now()

a user may simply set their system clock backwards.

So you have three levels:

Basic
Signed licence + local clock

Better
Signed licence + remember highest observed timestamp locally

Strongest
Signed licence + occasional trusted server timestamp
If you're adamant that OpenAutomation must run entirely locally, I'd use the middle approach and understand that it raises the bar rather than making bypass impossible.
