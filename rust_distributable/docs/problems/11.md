# Problem 11: the login's `AID` was hardcoded to the author's two accounts

## The problem (packets and database)

`lli` carries `AID`, the portal account id. `GameServer::connection()` returned one baked-in value
per server (US1 → one account's id, World 2 → another's), so every build sent the author's
portal identity in the login whoever was signing in. A friend on another account would have sent
`AID` values that are not theirs. The initialize form had no field for it and nothing was stored,
so there was no way to correct it short of editing the source.

## The fix

* `empire-daemon/src/direct/mod.rs`: the two constants are gone. `connection()` returns only the
  endpoint and server header. `InitializeAccountRequest` gains an optional `portal_account_id`.
* `empire-daemon/src/direct/portal_id.rs` (new): `resolve` picks the id just supplied, else the one
  remembered for that account, else generates a 19-digit portal-shaped one; `remember` stores it in
  `app_state` under `portal_account_id.<account>` so it is stable from then on. Nothing is added to
  the schema.
* Saved-account reconnects and "scan more" send only username and password, so they get the
  remembered id with no UI change. A different machine starts empty and learns it from its first
  sign-in.
* `empire-core/src/session.rs`: `LoginCredentials.portal_account_id` defaults to empty, and
  `/v1/direct` no longer rejects an empty one (a CLI-supplied id is sent as given).
* Desktop: an optional "Portal account ID" field on the initialize form.

## Why a generated id is safe: how pygge does it

pygge (`pygge/account/auth.py`, `lli` and the register call) sends one fixed `AID`
(`1674256959939529708`) for every account it logs in, and password logins work for all of them. So
the server does not tie `AID` to the account; it only wants an id of the portal's shape. The
older Python `.ini` flow required `account_id` only by its own convention.

Not verified here: this build has not been run against the live server with a generated id (no
credentials were available), and an *empty* `AID` is untested anywhere, which is why it is not used.
If a fresh account is refused at login, supply an id on the form and it is remembered.

## Same change: the builder's username in the binary

`strip = true` removes symbols, not panic-location strings, so the release binary held hundreds of
`/Users/<builder>/.cargo/registry/...` paths. `scripts/release.sh` now builds with
`--remap-path-prefix` for the cargo home, rustup home and repo root, and warns if the binary still
contains `$HOME`.

## First field test: "stuck initialising" was a missing licence plus a stuck button

The login itself worked (`lli` accepted, `gbd` handled). The session then failed with
`licence.needed: server WORLD2, player 596904, main castle (543, 520)` because the token had not
been added yet when the attempt ran; the UI called it "Needs attention" but left the Initialize
button on "Initializing…", since it was only re-enabled on success or a rejected request. The
button now re-enables when the phase is `failed` (`desktop/src/main.js`), so after adding the token
the same form can be submitted again.
