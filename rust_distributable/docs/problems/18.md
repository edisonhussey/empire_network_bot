# Problem 18: support was a separate switch, so a bot could say "support" and reserve nobody

## The problem (configuration)

Support (moving an attacked castle's troops to a safe spot) could be switched on in two unrelated places:

* **In the attack bot builder** a "Support (optional)" dropdown had to be chosen *before* the "Reserve commanders for support" button worked, and a bot could be saved with a support chosen and no commanders reserved. A support march then had no commander kept free, which is the case the reservation exists to prevent.
* **In the Control Panel**, after an attack bot was picked, a second "Support (optional)" dropdown appeared for the account. The note under it said the bot's own support "wins", so the field could be set and still be ignored.

Support worked when commanders were reserved for it (detection and the interruption sequence were fine); only the way it was switched on was confusing.

## The rule

**Support is on exactly when the attack bot reserves commanders for it.** Reserved commanders greater than zero: the bot is a hybrid and support is active. None reserved: a plain attack bot. There is no separate switch.

* **Builder** (`desktop/src/views/mode-builder.js`, `index.html`): "Reserve commanders for support" is always available. Reserving the first block reveals the one remaining choice, *where support waits* (a saved support, picked automatically when only one exists). Saving requires it while commanders are reserved. The board note reads "N kept for support · hybrid, support on". Removing every reserved block hides the choice and saves a plain attack bot.
* **Control Panel** (`desktop/src/main.js`): once an attack bot is chosen the account's Support dropdown is hidden and replaced by one line, either "Hybrid: N commanders kept for support… troops go to…" or "Attacks only: this bot keeps no commanders for support…". The dropdown remains only for an account with **no** attack bot (support on its own); starting a bot with an attack bot never sends a separate support.
* **Service** (`empire-daemon/src/plans.rs`, `support_from_reserved`): on save, no reserved commanders means `support_bot_id` is stored as none, whatever the form carried; reserved commanders without a destination is refused ("choose where support waits…").
* Pure helpers `supportCommanders` and `modeSupport` in `desktop/src/views/commander-ranges.js` hold the rule for the UI; tests in `commander-ranges.test.js`, and three Rust tests beside `support_from_reserved`.

## Not verified / left alone

* Not run in the app or against the game; the Rust workspace was not built here, only the new function and the JS tests were run.
* Attack bots saved earlier that name a support but reserve nothing are left in the database as they are. The Control Panel now describes them as "Attacks only", but the service still treats such a bot as carrying that support until it is saved again.
* Support on its own (an account with no attack bot) is kept. If it should go too, remove the dropdown and `station_bot_id` from the start request.
