# Problem 23: the handshake goes out of date after every game update (third time), so the service now reads the new versions itself

## The problem (packets)

The game ships a new web client every few weeks. Each time, the server refuses the version our handshake carries and
every login stops at `vck` ([problem 10](10.md): 1.169.11 to 1.170.22, [problem 20](20.md): 1.171.8 to 1.171.9). The
shape is always the same:

| Direction | Frame |
| --- | --- |
| client -> server | `verChk` `<ver v='166' />` |
| server -> client | `apiOK`, `rlu`, `joinOK` |
| client -> server | sys `login` (`pword` `<client version>%en%0`), then `vck` payload **`<client version>`** |
| server -> client | `vck` `<server build> / <api version>`, **status `1`** |

Since problem 10 no `lli` follows a refused `vck`, and the session ended at once with `connection.version_rejected`. The
fix each time was by hand: read the new version out of the public client, change `CLIENT_VERSION`, rebuild, reinstall.

On 2026-11-10 the user reported the handshake failing again. The versions read from the live client that day
(`client_versions` example) are `1.172.14` -> wire value `1172014`, and `verChk` `166` (unchanged). `CLIENT_VERSION` was
set to `1172014` in 0.1.77; `SMARTFOX_API_VERSION` stays `166`.

## Where the versions come from (deterministic)

Both version values in the handshake are written into the public client and computed the same way every time:

* **client version** (sys `login` and `vck`): `Game.bundle.<hash>.js` holds `name:"TranspilationEmpire",version:"A.B.C"`.
  `CastleVersionInformation` turns it into the wire value with
  `t=v.split("."); pad minor and patch (patch cut at "-") to 3 digits; A+B+C`, so `1.171.9` is `1171009`.
* **`verChk` version**: `dll/ggs.dll.<hash>.js` opens every socket with `sendXMLMessage(f,"verChk",0,"<ver v='166' />")`.
* `https://empire-html5.goodgamestudios.com/default/index.html` names both files (`href="Game.bundle.<hash>.js"`,
  `href="dll/ggs.dll.<hash>.js"`).

Checked against the saved client of 2026-10-14 (`data/raw/game_files/client/`): the code reads `1.170.22` and `166`, and
gives `1170022`, the value the live server accepted in problem 10.

## Fix

* `empire-core/src/client_release.rs` (new): parses the three files and applies the client's own rule (`derive`).
  Stricter than the client: a part that is not digits, or a minor or patch over three digits, derives nothing.
* `empire-core/src/session.rs`: `verChk` now sends `SessionSettings::smartfox_api_version` (default `SMARTFOX_API_VERSION
  = "166"`, serde-defaulted so saved settings still load) instead of a literal, so a derived value reaches all three fields.
* `empire-socket/src/client_release.rs` (new): `fetch_handshake_versions`, a one-shot HTTPS `GET` of the three public
  files over the TLS the game socket already uses (no new crate). Nothing is sent to a game server.
* `empire-daemon/src/direct/version.rs`: a refused `vck` no longer ends the session at once. It follows a schedule:

  | Refusal | Wait | Next attempt |
  | ---: | --- | --- |
  | 1 | 5 min | same versions |
  | 2 | 2 h | same versions |
  | 3 | 2 h 5 min | **only** with versions read from the live client after this wait, and only if they differ from the refused ones and are not older. Otherwise no attempt. |
  | 4 | | the session ends (`connection.failed`) |

  Each wait is from the refusal before it. No credentials are sent on any refused attempt (the core still stops at `vck`).
  Events: `connection.version_rejected`, `connection.version_retry_scheduled`, `connection.version_retry`,
  `connection.version_derived`. The window shows `bot_state` `waiting for game update` during a wait.
* Derived versions the server accepts are kept in `app_state` `handshake.accepted_versions` and used by later sessions,
  until a build ships a newer `CLIENT_VERSION` (the higher one wins).
* `empire-daemon/src/direct/mod.rs`: the reconnect loop sends a refusal to that schedule (separate from the lost-link
  budget) and applies the remembered versions at the start of a run.
* New `cargo run -p empire-socket --example client_versions [url or folder]`: prints the versions the live (or a saved)
  client yields next to the built-in ones. It does not contact a game server.
* App 0.1.77.

Tests (no live server): the padding rule against both values the server accepted before; derivation from the saved client
files; a page that changed shape derives nothing; the HTTP reader (length, chunked, redirects, short bodies) and a full
fetch from a local server; the schedule with a mocked clock (waits 300 s, 7200 s, 7500 s; the client read once, after
the last wait; no fourth wait); no final attempt when the client is unchanged, older or unreadable; remembered versions
carry over until a newer build.

## What was not checked

* That the server keys only on these values. Problems 10 and 20 both were only the client version; if the next update
  changes something else in the handshake (a new field, a different `vck` shape), the final attempt will still be refused
  and the session ends after it as before.

## When it happens again

The service now recovers by itself on the third attempt (about 4 h 10 min after the first refusal) if the client changed
only its versions. To skip the wait: run the `client_versions` example, put the value in `CLIENT_VERSION` (and
`SMARTFOX_API_VERSION` if it changed), confirm with the `vck` example, rebuild and reinstall.
