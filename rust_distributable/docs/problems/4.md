# Problem 4: recording other players' movements from `gam` and `mrm`

Building the PVP tab ran into five things the packets and the database did not make
obvious. Each is listed with what was found and how it is handled.

## 1. `gam` does not say who we are

A `gam` names a sender and a target but never the observing account, so "incoming" cannot be
read from the packet alone (`incoming_gam.md` says as much). The target's alliance id alone does
not show it is *our* alliance.

**Fix.** The login `gbd` carries `gpi.PID` (player) and `gal` (`AID`, `N`: our alliance). It is
stored per account in `account_alliance` (migration V21). A movement is then judged against it:
sender and target alliance ids, plus the target's `(kingdom, x, y)` against the account's owned
castles. A `gam` that arrives before the identity is known is skipped, not guessed, because a
stored classification is never revised.

## 2. The same MID changes shape

In captures one MID first arrives with `GS` and later with `GA` (flank lists of
`[unit, count]`), with the same `TT`. `GS` is not a unit count, so the army is unknown at first.

**Fix.** `army_size` is `NULL` until a `GA` appears, summed over `L`, `M`, `R`, `RW`. The insert is
`INSERT OR IGNORE`; a repeat packet only fills columns that are still `NULL` (`COALESCE`), so
timestamps and classification stay as first seen. Repeat packets cannot create duplicates or move a
landing time.

## 3. A landing time is only an estimate, and a retreat voids it

`PT`/`TT` give the remaining time at observation; arrival is never confirmed by a packet. A
retreated movement never lands at all.

**Fix.** State is derived from the clock when read (`active` / `landed`), and `retreated_at_ms`
overrides both. A retreated row shows when it was recalled, not a landing time, and is counted
under `retreated`, never `landed`. Nothing is stored that has to be ticked forward.

## 4. `mrm` is ambiguous

The capture is one frame with only a `MID`, so it is unknown whether it is a request or a
confirmation, or whether the server sends one when another player retreats. It names any MID,
whoever owns the movement.

**Fix.** Only an inbound `mrm` with status `0` marks a recorded MID retreated (final; a second one
changes nothing). Our own outgoing frames are not read. An `mrm` for a MID we never recorded is
ignored. If captures later show the server does not push `mrm` for others' retreats, the open
risk is a called-back attack staying "active" until its time passes.

## 5. History must not live in memory

Incoming movements grow without bound and are wanted as history.

**Fix.** One row per `(account_id, mid)`, indexed by `(account_id, detected_at_ms, mid)` for
keyset paging and `(account_id, kingdom_id, land_at_ms)` for the map. `GET /v1/pvp` returns one
page; counts are computed in SQL. The window holds one page and fetches older ones on request.
Rows are kept indefinitely (about 250 bytes) and are not cleared by "reset account".

See `docs/architecture/pvp.md` and `docs/network_packets/alliance_fields.md`.
