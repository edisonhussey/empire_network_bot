# Problem 28: no attacks for 9 minutes; every pick froze the session for about 10 seconds

## The problem (packets / db)

2026-11-16 08:27 to 08:36, ventrilo: the refinery visit ran, then no attack was sent. Every minute the attack bot opened the
Burning Sands map (`gaa`), and 60 ms later the recruit bot opened a castle (`jca`). Then: "map window never answered", three
times, and the response-health safety pause.

## Cause

Choosing a tower (`Store::reserve_rbc_target_with`) and the kingdom-grouping wait (`RBC_NEXT_READY_SQL`) asked the ledger
"was this tower attacked recently" once per tower with `WHERE lower(a.account_id) = lower(rbc_target.account_id)`. A function
over the column stops SQLite from using `attack_ledger_target_idx`, so each tower scanned the whole ledger. Problem 22 fixed
this in the map query, but not in these two. With 98,000 ledger rows and 340 towers, one pick took **10.5 s** (measured on a
copy of the live database). It runs on the single writer connection, inside the session loop, so the loop handled no frames
for that time. The attack bot's map request went out with a deadline that had already passed, so it "timed out" at once. The
connection looked silent, the recruit bot (now free) switched castles, and the map reply arrived into the wrong view.

Not caused by the refinery or the injection work; it grew with the ledger and crossed the line today.

## Fix

`empire-core/src/store.rs`: both queries are constants (`RESERVE_RBC_CANDIDATES_SQL`, `RBC_NEXT_READY_SQL`) that compare the
account as stored (`account_id = ?`, `a.account_id = rbc_target.account_id`), as every write stores the canonical id (V7, V28).

## Verified

* The same query on the live copy: 10.5 s → 0.066 s (sqlite3). A full pick on the copy: 8.3 s → 0.25 s.
* `pools_tests.rs`: both plans use `attack_ledger_target_idx` and never scan the ledger.
* `cargo test --workspace` passes.

## Check next time

Other `lower(account_id) = lower(?)` filters remain on small tables (`rbc_target`, `fortress_target`); they are not per-row
subqueries over the ledger. A pick slower than a second shows as a sqlx `WARN` in the daemon log when `RUST_LOG` is set.
