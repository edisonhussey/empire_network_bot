# Problem 12: the robber baron level is not in any packet (and the session reader leaked SQLite files)

## The problem (packets)

We wanted the level of a robber baron castle, and how many attacks until it levels up, from the map
data. The `gaa` entry for one is `[2, X, Y, -1, count, cooldown, KID]`, for example
`[2,647,637,-1,11,-9368850,0]`, and nothing in it, in `adi`, or in `sdi` says "level 8". The in-game
castle info showed level 8 with 3 attacks to go for that castle, so the level is computed on the client.

Guessing it from screen readings was not safe. Seven readings (counts 0, 4, 7, 9, 11, 13, 14) gave levels
1, 5, 6, 7, 8, 8, 9, which fit several different tables for the counts nobody had looked at, and nothing
told us how the levels continue past 10 (the worry was level 60 from a level 80 reading). The `11` in
field 4 is not the level either; it is the victory count.

## How we found the rule

1. `proxy_packet_monitor` can now save the game's own downloads while a "Download login data" checkbox is
   on (see its README). The first try saved nothing because the browser had the files cached and sent
   `If-None-Match`, which got a bodyless `304`. The capture now strips `If-None-Match` and
   `If-Modified-Since` on the game hosts, and a hard reload fetched everything (496 files, 46 MB).
2. The items file (`items_v787.03.json`) has a `dungeons` list, but it only describes the *defenders* per
   victory count, not levels.
3. The client code did have it. `Game.bundle` parses the entry (`_victoryCount = e[4]`,
   `_dungeonLevel = DungeonConst.getLevel(...)`), and `ggs.dll.*.js` holds `DungeonConst`.

The rule, now documented in [`game_infrastructure/robber_baron_level_formula.md`](../game_infrastructure/robber_baron_level_formula.md):

```
level = floor(1.9 * count ^ 0.555) + offset(kid)      offset: KID 0 -> 1, 2 -> 20, 1 -> 35, 3 -> 45, else 0
attacks to next level = floor(((level - offset + 1) / 1.9) ^ (1 / 0.555)) + 1 - count
```

All seven readings match it exactly. It also settles the question of how the levels continue (level 60
starts at count 489 in kingdom 0). The "different schema" between kingdoms is only the offset; the entry
layout is the same.

## The problem (database)

While reading the capture we hit a separate fault in the packet monitor's session store
(`proxy_packet_monitor/backend/storage.py`). `list_sessions`, `events`, `event` and `export_session` used
`with sqlite3.connect(...) as conn:`, which commits but **does not close**. The web page polls the session
list every few seconds, so the process kept opening every recorded session file (33 files, about 8 file
descriptors each, 281 after under two minutes).

It went unnoticed from a terminal (a high descriptor limit) and failed as soon as it ran under the
process monitor's launchd job, whose default limit is 256: `OSError: [Errno 24] Too many open files`, the
"Start proxy" request failing, and then the whole page hanging.

Fix: every read now uses `with closing(sqlite3.connect(...)) as conn:`. `run.sh` also raises the limit to
10240 for the page and the mitmdump it starts. Measured after the fix: 120 requests to the session
endpoints, 36 descriptors held, flat.

## Three smaller faults found on the way

* The proxy's "did it open yet" check gave up after 1.5 s but a cold start takes 1.3 to 5.6 s, so the page
  reported "Proxy did not open". It now waits up to 30 s.
* The "port already in use" probe bound without `SO_REUSEADDR`, so closing browser connections left in
  `TIME_WAIT` on 8080 made a restart fail although nothing was listening. It now sets `SO_REUSEADDR`
  like the proxy itself does.
* A recording command left in `control.json` was replayed every time the proxy started, switching
  recording on by itself (and producing empty sessions). The addon now ignores a command that was already
  there at startup.

## Not verified

* Only kingdom 0 was checked against in-game readings. The offsets for the other kingdoms come straight
  from `DungeonConst.getKingdomOffset` and were not compared with a screen.
* The in-game names for kingdom IDs 1 and 2 (Burning Sands and Everwinter) are matched from the items
  file's internal names (`Dessert`, `Icecream`); the offsets do not depend on that matching.
* The count-to-level curve is part of the client build (items version 787.03). If it changes in an update,
  recapture and re-read `DungeonConst`.
