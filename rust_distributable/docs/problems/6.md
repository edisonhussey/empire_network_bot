# Problem 6: running more than one account at a time

Ventrilo had to stay up (it is in protection) while other accounts were tried in the same
production install. The service held a single game session, so signing a second account in
ended the first. Making it hold several exposed state that had been quietly global.

## 1. One slot for the session

`AppState` held one `direct_status`, one `direct_task`, one injection queue and one
diagnostic snapshot, and `POST /v1/direct` aborted the old task. `direct::run` itself was
already per account (its login lock, ledger, commanders and targets are all keyed by
`account_id`), so only the service's bookkeeping was single.

**Fix.** `sessions.rs` keeps a session per canonical account id, each with its own status,
queue, snapshot and task; connecting replaces only that account's. The API takes
`account_id` where a session is meant. Ending a session ends that account's bots only.

## 2. State that looked per-account but was not

* The recent-packet table was capped at 200 rows **in total**: two busy accounts would each
  keep about half, and a quiet one would lose its history. It is now capped per account.
* The "is the run alive" heartbeat was one key (`hunt.heartbeat_ms`), so one account running
  made every account look alive. It is now `hunt.heartbeat_ms.<account>`; the standalone
  hunter keeps the plain key.
* The Overview's refresh request was one key, so asking for one account's castles made every
  session send a `dcl`. It is now per account.
* "Which account?" was answered by reading the one status. Handlers now name the account, and
  with none named fall back to the only (or most recently) connected one, never a guess.

Each has a test (`store/tests.rs`, `sessions.rs`).

## 3. Licences were global, tiers were not

`licence.require(feature)` passed if *any* installed licence allowed it, so a free account
would have inherited a pro account's automation. Licences were already one per account and
bound to a player; the session now records the tier and features of **its own** licence and a
bot starts only when that licence includes `automation` (`plans::require_ready_account`). A
single token for several accounts was not built: it needs a new token schema and the issuing
tool.

## 4. A window written around one account

`main.js` kept one `latestDirect` and several views assumed "the connected account". Rather
than rewrite them, `latestDirect` is now the status of the account in view
(`account-context.js`), and each view reads the account from that one place: Control Panel
shows one card, Initialize one account's scan plan, Logs one account's packets. A header menu
switches the account without touching any session. The bot menu now also preserves the
auto-station choice when it starts a bot (it used to send only the attack and recruit bots,
which would have cleared it).

## 5. Seeing one account from another, without leaking

To watch an attack, the support send and the retreat from another account's tab, the
Development maps are shared between accounts, but only on the same world: an account on
another world must never appear. The service decides (`dev_shared.rs`): the viewed account
plus every signed-in account on the same game endpoint. Accounts in one alliance record the
same movement, so threats are merged by MID and drawn once, in the colour of the account they
concern.

## Deploying the change

The service API version is 50. A window of this build replaces a running older service when it
opens, which ends every live session. Restart accounts afterwards (an account in protection
included) and choose the right one in the header.
