# Problem 26: refined wood and stone had to be crafted by hand

## The problem (packets / db)

The person crafts 100 refined wood and 100 refined stone at the Green main castle's refinery, one at a time, each an
hour, by hand. The packets were captured on 2026-11-16 ([`crst`](../network/crst.md), [`crin`](../network/crin.md)) and a
manual test through the proxy injector (two `crst`, wood then stone) worked.

## The fix (0.1.78, schema 29, API 57 unchanged)

A **resource bot** with one job, the refinery ([`architecture/resource-bot.md`](../architecture/resource-bot.md)):

* Resources tab: *Create refined resource* (tick refined wood, refined stone or both) and *Create resource bot*.
* Control Panel step 2: *Resource bot*, none or one, started and stopped with the other bots.
* The session opens the Green main castle (`jca`), reads the refinery (`crin`) and the stock (`dcl`), checks every craft
  against the stock **before** sending anything, sends the `crst`s 1.5 to 9 s apart, logs
  `checking inventory for castle NAME (ID) -> (wood N, stone M; refinery F of 2 free) -> executing refined wood, refined stone`,
  and returns to the map (`gaa`).
* Next visit when the refinery is empty, at least 2 h later; stored in `refinery_state`, so it survives restarts.

New tables (`V29`): `create_resource_preset`, `resource_bot`, `account_resource_bot`, `refinery_state`.

`API_VERSION` stays 57 on purpose: only routes were added, and a bump would make the installed app (still 57) replace the
newer daemon that process_monitor runs. Bump it with the next DMG.

## Verified

* `empire-core`: plan/affordability/next-visit/`crin` parsing tests; store tests for presets, bots, the running choice and
  the schedule.
* `empire-daemon`: a full visit driven by the captured replies (`jca` → `crin` → `dcl` → `crst` ×2 → `gaa`), the
  stagger bounds, the saved schedule, a restart not visiting early, too little stock sending nothing, a stopped bot doing
  nothing, and the log line.
* `npm test` for the tab's helpers.

## Not verified

* A live run through the bot (only the injector test was live).
* The server's answer to `crst` with a full queue or short resources (the bot avoids both, but a stale `dcl` is possible).
* That `jaa` carries the castle id at `gca.A[3]` for the main castle (the recruit bot relies on the same field).
