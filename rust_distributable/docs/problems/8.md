# Problem 8: commanders that vanished, returns that never came, troops the tables did not know

Packets and database problems met while adding support to attack bots, and how each was fixed.

## 1. Eighteen commanders, seventeen usable

An account with 18 commanders and 17 assigned showed one free, then refused the 18th.

**Cause.** The roster was a hand-kept list of "usable" logical commander ids, taken from one
account (Ventrilo). Logical ids are per account, so on pingpoko the list dropped its commanders 5,
12 and 19, and "commander n" no longer meant the n-th commander.

**Fix.** The account's own `gli.C` is the roster, ordered by each commander's `VIS` (the position
the game shows; without it, list order). Human number n is the n-th of that list, and the map
number to logical id lives in the account's data, not in a table. Barons (`gli.B`) are not
commanders.

## 2. A march whose return was never heard

If the session dropped for 5-20 minutes, the `mrm`/return packet for a landed attack was never
seen, and the ledger kept the march outbound for good, so commanders and map blocks stayed stuck.

**Fix.** The return cannot take longer than the trip out. `lapse_stale_marches` (at session
start and every 30 s) marks a landed march lapsed once `sent + 2 x duration + 15 s` has passed
(`march.lapsed`), freeing its commander; the Troop overview and the map show it as an estimate
before that. A real return arriving later still matches its march.

## 3. A support send refused for troops the tables did not know

On pingpoko the incoming attack was seen but the move to the support spot failed: `cds` carried
unit ids 215 and 227, which the unit catalogue lacks, and the ids were dropped or the whole
send refused (a support takes at most 10 distinct unit types).

**Fix.** Sort the castle's units by quantity, keep the top 10 types (unknown ids included, since
the server knows them), and if the server refuses a send with unknown ids, resend once with
only the known ones. An uncertain `cds`/`mcm` is never repeated.

## 4. Reserving commanders for support

`automation_mode_reserve` (migration V24) keeps support ranges in board order next to the
tasks; `active_mode_tasks` and `choose_support_lid` read the same slots, so a task never takes a
reserved commander and a support send prefers one.
