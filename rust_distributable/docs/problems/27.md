# Problem 27: the bot could only run on its own socket, and could not be paused without dropping it

## The problem

Developing against the live game meant a fresh login per change. The person wanted the same bots to run over a browser
session already playing through proxy_packet_monitor (easier to watch and develop in real time), without touching the
standalone bot. They also wanted to stop the bots for inspection without losing the socket. No packet or table changed.

## The fix (0.1.78, API 57 unchanged, schema unchanged)

* **One engine, two transports** (`direct/link.rs`): `run_inner` now reads and writes a boxed sink/stream. Direct mode
  wraps the same `empire_socket` socket as before; injection mode wraps channels fed by `GET /v1/attach` (`attach.rs`).
  In injection mode the login, the heartbeat and reconnects are skipped, and the identity the last direct login stored
  (`app_state` `session.identity.<account>`) binds the licence.
* **Pause** (`direct/pause.rs`, `POST /v1/direct/pause`, Control Panel button): bots stop sending, every frame is still
  read; a step in flight is abandoned as a failure through each bot's new `interrupt`.
* **Human hold**: in injection mode, a view command the person sends in the browser pauses the bots for one minute, same
  rules.
* **Proxy side**: `backend/openauto_link.py` (wsproto client inside mitmproxy) and a **Start injection bot** button.

See [`../architecture/injection-mode.md`](../architecture/injection-mode.md).

## Verified

* `cargo test --workspace` (link both ways and ending with the proxy, pause rules) and the existing 170 daemon tests, so
  the direct path behaves as before in every test that drives it.
* proxy_packet_monitor unit tests (80), including the link's message format and its local-only target.

## Not verified

* A live injection session end to end (browser → proxy → daemon → bot frame back to the server).
* That mitmproxy marks frames it injected toward the server as `injected`, which keeps the bot's own frames from counting
  as the person acting (documented mitmproxy behaviour, not observed here).
* A session attached before the account ever logged in directly is refused by design.
