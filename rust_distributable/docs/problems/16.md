# Problem 16: the game's data was copied by hand under other names, so ids were missed and nothing could be looked up

## The problem (data and naming)

The Rust troop and tool tables were generated once from the old Python bot's data. That left three faults:

* **Incomplete.** They held 257 troops and 294 tools. The game's own `units` table (the items file, version 787.03) has 1,001 units: 473 troops and 528 tools.
  In a real account's castles, five stacks were unknown to the code, among them 215 "Shield-maiden" (974,901) and 227 "Protector of the north" (229,693). The
  Overview showed them as `unit 215` under "Other".
* **Other names.** The tables used the Python bot's names and fields (`ranged_defence`, `loot_capacity`, `valkyrie_ranger_9`) where the game says `rangeDefence`,
  `lootValue`, `MeadRanger`. A field seen in a packet, a file or the client could not be found in the code by the same word.
* **Stale and scattered.** About a tenth of the old defence and loot values differ from the live game, there was no single file to look an id up in, and the
  kingdom rates and skip items came from a separate script (`gen_travel_costs.py`) beside the retired `gen_game_data.py`.

## The fix: one pipeline, the game's names

```text
data/raw/game_files  ->  utils/scripts/build_tables.py  ->  data/tables/*.csv  ->  generated/{units,rules}.rs  ->  empire_game::{unit_by_id, kingdom_rule, minute_skips}
```

* `data/raw/` holds the originals (git-ignored); `data/tables/` holds the small tables built from them (committed): `units.csv` (all 1,001 units, all 100 game
  columns), `kingdoms.csv`, `minute_skips.csv`, `meta.json` (which items and language file they came from, with hashes), and two hand-kept bridges in `legacy/`.
* **Columns and Rust fields use the game's names** (`kingdomTravellingCost` is `kingdom_travelling_cost`); added columns are snake_case (`display_name`,
  `legacy_name`) so they are never mistaken for game fields. Every id keeps its old name in `legacy_name`, so old code and old docs stay findable.
* `crates/empire-game`: `units.rs` and `rules.rs` (types and lookups) over generated rows. `kingdom_travelling_cost` now reads the units table; the transfer rules read
  `kingdom_rule` and `minute_skips`. The old `travel_costs.rs` and its generator are gone.
* `station::unit_label` gives the Overview and Troop overview the game's names and its own troop/tool split (`role`), so the missing ids now read properly.
* `unit_art.csv`: the picture path of all 1,001 units, from the client's own naming rule (`<name>_<group>_<type>`) and its art table in `ggs.dll`; the images themselves are not in the copy.
* Getting the pictures: `proxy_packet_monitor` gained an **Include images** option for the login capture; `organize_game_data.py` places images and gives every captured URL its own path (identical bytes are stored once by the capture), and the art tables record which pictures are in the copy. 237 pictures were captured (all `.webp`; an earlier note here and the first `png_url` column wrongly said `.png`, corrected), and every one matches its descriptor's declared size; 70 are tied to entities (buildings), none to a unit yet.
* Tests: `crates/empire-game/tests/unit_tables.rs` fails if a generated row differs from its CSV row, if any old id or name is lost, or if the game's troop/tool
  split disagrees with the old tables (it agrees for all 551). Manual: [`../game_data/tables.md`](../game_data/tables.md).

## Left alone on purpose

What the bot **sends** is still decided by the older tables: the attack catalogue, the support army (`unit_kind`) and the support fallback (`known_troops_only`).
The complete table knows units the bot has never sent, so switching eligibility to it would change live behaviour. That needs an explicit decision (an "allowed to
send" column, reviewed), not a data migration. A test pins the split: 215 is a troop on screen and still not a known troop to send.

## Not verified

* The tables and Rust were verified against each other and the old tables, not against the running app: the Overview and Troop overview names were not looked at on screen.
* Only 23 of the 103 `units.csv` columns have a written meaning (about a fifth); the rest are listed as undocumented in `tables.md`, not guessed.
* Display names exist for 826 of 1,001 units (the rest have no `<type>_name` in the language file); those show their internal `type`.
* The art paths follow the client's table and agree with the one captured descriptor; no image URL was fetched, so whether the server serves each one is unconfirmed.
* The kingdom, troop and tool tables the bot's attack builder uses are still the older ones, so their values can differ from the live game by about a tenth.
