# Problem 13: green towers never fired (no level), and kingdoms were alternated

## The problem (packets and database)

**Green never attacked.** A task carries a level band, and selection only takes towers whose
stored `level` is inside it (`level >= min AND level <= max`). The `gaa` row of a tower is
`[2, x, y, -1, count, cooldown, kid]`: it carries the **victory count**, not a level, and the
code turned it into a level only for Sands (`kingdom_id == SANDS_KINGDOM_ID`, with a private
copy of the formula in `account.rs` and another in `hunt.rs`). Every other kingdom was stored
with `level = NULL`, and `NULL >= 1` is not true in SQL, so a green task with any band saw
"no towers in range" however many were ready.

**Kingdoms were alternated.** Tasks were tried in plain rotation and each belongs to one
kingdom, so fire, green, fire, green: every attack in a kingdom other than the client's current
one costs a `gaa` to enter it.

## The fix

* `empire-core/src/dungeon.rs` (new): the client's own rule, for every kingdom: level =
  `floor(1.9 * count^0.555) + offset` (offsets 1 / 35 / 20 / 45 for green / sands / ice / fire),
  plus `hits_to_next` and `progress`. The two private copies now call it. See
  [`../game_infrastructure/robber_baron_level_formula.md`](../game_infrastructure/robber_baron_level_formula.md)
  for where it was read from and the in-game readings it reproduces.
* `account::rbc_targets` now gives every type-2 row a level and keeps the raw `victory_count`.
* Migration **V25** adds `rbc_target.victory_count` and `hits_to_next` (the schema only had
  `level`, from which the count cannot be recovered: many counts share a level), and drops the
  stored scan windows once so existing towers are read again and filled in.
* `store/dungeon.rs` (new): `record_rbc_victory` adds one win and recomputes level and
  `hits_to_next` in one transaction. `apply_attack_return` calls it for a return that brought loot
  and matched an in-flight march, so a replayed return cannot count twice, and no map scan is
  needed between attacks. A tower whose count was never read is left alone.
* `empire-core/src/grouping.rs` (new) and `automation.rs`: tasks in the kingdom the client is
  in go first, a short wait in that kingdom is preferred to a switch, and a cap hands the turn
  over. Settings are the app-state key `automation.kingdom_grouping`. See
  [`../architecture/kingdom-grouping.md`](../architecture/kingdom-grouping.md).

## Not verified

* **Never run against the live server.** Tests cover the rule (the seven green readings, plus
  Fire Peaks and Everwinter checks from captured rows), the storage and increment path, and the
  grouping decisions through the real `next_packet`. Nothing here was sent to the game.
* The Great Empire was compared with seven in-game readings. Fire Peaks and Everwinter got one
  check each (a tower's computed level and hits to go were given to the user, who answered
  "perfect" without quoting the screen); Burning Sands rests on the documented raw 112 = level 61.
* Whether a won attack always adds exactly one to the count is inferred from one observed
  2 -> 3 step; other players' wins are only learned at the next scan, and the server's number
  replaces ours then.
* The grouping defaults (`max_streak` 12, `patience_s` 120) are guesses to be tuned.
