# Problem 22: both sessions died on `pool timed out` together, and every view was slow (one database connection)

## The problem (packets / db)

Both accounts ended for good in the same instant, and the app had been getting slower for days:

| Time (UTC) | Account | `event_log` |
| --- | --- | --- |
| 2026-11-02 05:16:32.053 | ventrilo | `connection.failed`: `pool timed out while waiting for an open connection` |
| 2026-11-02 05:16:32.053 | pingpoko | `connection.failed`: same error, **the same millisecond** (`at_ms` 1793596592053) |

* pingpoko had been connected since about 02:20 (about 3 h); ventrilo since about 04:54.
* No `connection.lost`, no `connection.retry`: the session was ended, not reconnected. [Problem 21](21.md) made `PoolTimedOut` a
  retryable error in 0.1.74, so either the service still running was older than 0.1.74 (the stale-service trap of
  [problem 20](20.md)) or the retry did not apply. This was not checked on the machine.
* The same error had already ended ventrilo at about 01:38 the same night.
* The map of activity took about 50 s to draw and the Castle Overview about 20 s. The overview handler runs three tiny queries,
  so its 20 s was time spent waiting, not working.
* The `march.lapsed` rows ("N marches closed as home: their return was never reported") after each reconnect are a
  consequence, not a cause: returns that land while a session is down are never seen.

## Cause

Two things, one on top of the other.

1. **One connection for everything.** `Store::open` used `max_connections(1)`. Every query from every session and every
   view shared it, and a caller that waited past sqlx's 30 s acquire timeout got `PoolTimedOut`. So the first slow query
   stalled all the others, and when it ran long enough every waiting session timed out at the same moment (the identical
   millisecond above).
2. **A query that was quadratic.** `Store::map_towers` (`GET /v1/dev/map`) asks the ledger, once per tower, for the latest march
   sent at it, with `WHERE lower(a.account_id) = lower(rbc_target.account_id)`. A function over the column makes SQLite
   ignore the index on `attack_ledger (account_id, sent_at_ms)`, and even that index never covered `(kingdom_id, x, y)`. Each
   tower therefore scanned the whole ledger: cost = towers x ledger rows.

Measured on a synthetic database shaped like the real one (release build, same machine):

| | before | after |
| --- | --- | --- |
| `map_towers`, 4,000 towers, 150,000 ledger rows | **121.3 s** | 0.04 to 0.07 s |
| a packet write issued while that read runs (800 towers, 30,000 rows) | **waited 5.17 s** (the whole read) | 0.004 to 0.007 s |
| 300 packet inserts, nothing else running | 0.26 s | 0.03 to 0.10 s |

At 121 s the write would have waited past 30 s and failed, which reproduces the log line exactly. A packet insert on its own
takes under a millisecond, so writing was never the slow part; reading was, and it held the only connection.

**Not verified on the live database.** The folder holding it was not readable from the session, so the table sizes above are
assumed (a 43 MB file, 4,000 towers and 150,000 ledger rows are plausible, not measured). The synthetic run shows the cost
grows with towers x ledger rows; it does not prove the real file reached 50 s for that reason alone. Nothing in the 05:16
event rows names the statement that held the connection (see "Check next time").

## Fix

All changes keep to the module they belong in.

* `empire-core/src/store/pools.rs` (new): **one writer, four readers.** The writer is a single connection, so writes stay
  strictly ordered and SQLite never answers `SQLITE_BUSY` to a transaction that reads first and writes second. The readers are
  `query_only` connections that open on first use; in WAL mode they neither block the writer nor are blocked by it. Both use a
  30 s `busy_timeout` and `synchronous = NORMAL` (the documented WAL setting: an app crash cannot lose a committed write; a
  power cut can drop the last few commits, which the game state re-learns). A database with no file (`sqlite::memory:`) still
  uses one shared connection.
* `empire-core/src/store.rs`: `Store` keeps `pool` (the writer) and gains `read_pool` with a `reader()` accessor.
  `empire-core/src/store/*.rs`: every method that only reads (72 of them, found by a script that skips anything containing
  `.execute(`, `.begin()`, or a write keyword) now calls `self.reader()`. Everything else is untouched.
* `empire-core/src/store/dev.rs`, `station.rs`: `map_towers`, `main_castle`, `account_world` and `overview_castles` compare the
  account as stored (`canonical_account_id` is what every write uses, and V7 normalised old rows) instead of through
  `lower(column)`. `map_towers` is now the constant `MAP_TOWERS_SQL`.
* `empire-core/src/store/schema.rs`: **V28** (`SCHEMA_VERSION` 28): index `attack_ledger_target_idx (account_id, kingdom_id, x, y)`
  and a safety net that lower-cases any `attack_ledger.account_id` that was not (`UPDATE OR IGNORE`, so a row whose canonical
  twin exists is left alone). `record_march` now stores the canonical id too.
* `empire-daemon/src/lib.rs`: `API_VERSION` 55 to 56, so the next window replaces a service that is still running from before this
  change instead of reusing it. Nothing in the HTTP API changed.
* Tests, in `empire-core/src/store/pools_tests.rs`: reads see committed writes and never uncommitted ones; the read pool refuses
  writes; writes do not wait for busy readers and reads do not wait for a busy writer; the in-memory store still works; the map
  query's plan uses `attack_ledger_target_idx` and never scans the ledger; V28's casing rules; and two sessions writing while three
  views read, with no error.

Not changed on purpose: `account_summaries` (about 0.12 s on 24,000 targets and 30,000 scan windows, and it now reads on its own
connection) and `dashboard_summary_for` (0.11 s on 150,000 ledger rows). Both still scan, and both grow with the data; they are the
next candidates if the Accounts or Dashboard views slow down.

## After installing

* The new app starts its own service because `API_VERSION` moved. Confirm with `curl -s 127.0.0.1:47821/v1/health`: `api_version`
  is 56 and `ps -p <service_pid>` shows the new binary. If it is not 56, quit the old service first (the trap in problem 20).
* The first start applies V28, which builds one index over `attack_ledger`; it takes a moment on a large ledger.

## Check next time

* sqlx logs any statement slower than one second at `WARN` with the SQL text (target `sqlx::query`). A line like that is the
  statement that held a connection; this is what was missing when nothing named the culprit. Keep `warn` enabled for `sqlx`.
* `connection.failed` with `pool timed out` should now mean the **writer** was held for 30 s: look for a slow statement line
  first, then for a long `VACUUM` (`prune`, `reset_account`, `wipe_all` all end with one; nothing calls `prune` on its own).
* `connection.lost` followed by `connection.login_ok` after a pool timeout is the problem 21 retry working.
