# Problem 24: the staged handshake retry never ran, because the failure was not a `vck` refusal

## The problem (packets / db)

0.1.77 ([problem 23](23.md)) added the staged retry (5 min, 2 h, then 2 h 5 min with versions read from the live client).
On 2026-11-11 both accounts dropped and stayed down, and the staged retry never ran. `event_log` (UTC):

| Time | Account | Event |
| --- | --- | --- |
| 12:34:41 | ventrilo (us1) | `connection.lost`: `Connection reset without closing handshake` |
| 12:34:58 | pingpoko (world2) | `connection.lost`: same |
| 12:35:47 / 12:35:59 | both | retry 1: `connection.lost`: `IO error: WebSocket framing error: RSV2 or RSV3 set` |
| 12:40:25 / 12:40:38 | both | retry 2: same, then `connection.gave_up`: `gave up reconnecting after 2 retries` |

On 2026-11-10 at 10:27 to 10:33 the morning of the game update (1.171.9 to 1.172.14) looked exactly the same. It was fixed
only by the 16:23 reinstall. No `vck` was sent or received in either window: `network_message` has no `vck` row after
October. The live client still reported `1172014 / 166` on 2026-11-11, so this was not a new client version. The Mac did not
sleep (`pmset`: no sleep since 2026-11-09 21:37).

## Cause

Two faults, one hiding the other.

1. **The staged schedule only applied to a `vck` refusal.** While the game's servers restart, the link dies before `vck`
   (at the upgrade). That was classed as an ordinary lost link, so it got the old budget of two retries (about 1 min and
   5 min) and then gave up. That is far too short to outlast a restart.
2. **The upgrade's error page was read as WebSocket frames.** `InflatingStream` (`empire-socket/src/stream.rs`) switched
   to frame mode after the upgrade response's blank line, whatever the status was. A `503` page's body (`<html>`, and
   `<` is 0x3C) then failed the inflater's header check with `RSV2 or RSV3 set`. That hid the server's real answer.
   Reproduced in a test: before the fix, a 503 upgrade answer gives exactly `IO error: WebSocket framing error: RSV2 or
   RSV3 set`.

## Fix

* `empire-socket/src/stream.rs`: frames follow only a `101` status line. Any other answer is passed through untouched,
  so `tungstenite` reports `HTTP error: 503` (or whatever the server said). Test:
  `a_server_that_refuses_the_upgrade_reports_its_http_status`.
* `empire-daemon/src/direct/mod.rs`: `failed_in_handshake`. A `vck` refusal, **or a link lost before the login was
  accepted** (`DirectStatus::authenticated`, internal, set at `login_ok` and cleared before each attempt), goes to the
  staged schedule in `version.rs`. A drop of a session that had logged in keeps the quick reconnect first. A database
  `PoolTimedOut` keeps the ordinary path. Test:
  `a_link_lost_before_the_login_is_a_handshake_failure_and_gets_the_staged_schedule`.
* Events: `connection.handshake_failed` (a failure that was not a refusal), `connection.handshake_retry_scheduled`,
  `connection.handshake_retry`. The window's `bot_state` reads `waiting for game update`.
* App 0.1.78.

How 2026-11-11 would now run: 12:34 drop, then a quick retry at about 1 min. That retry fails before login, which is
handshake failure 1, so the next try is at +5 min. If that fails, the next is at +2 h, and then once more at +2 h 5 min,
but only if the live client shows new versions.

## Not checked

* What the servers actually answered at 12:35 (the old build hid it). The next outage will log the HTTP status.
* Whether a restart ever lasts longer than the 5 min + 2 h window. If it does, and the client did not change, the session
  ends after the 2 h attempt, as specified.
