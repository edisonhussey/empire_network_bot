# Problem 2: a second account could not be licensed

8 Oct, ~07:27. Pingpoko (WORLD2) was connected and refused. The window showed
"licence is bound to a different game account". Found from the live service
(`/v1/direct`, `/v1/licence`) and the new `event_log` table, which recorded the
attempt (`connection.connected` then `connection.failed`, one second apart).

## Verdict

It was **not** the main-castle coordinates, and not a bad token. The app could only
hold **one** licence, and that one belonged to Ventrilo.

* Installed: `ventrilo-stage0`, bound permanently to server **US1**, player
  **16862926** (`licence_activation`, set 5 Oct).
* Pingpoko logged in on **WORLD2** as a different player. `bind_or_validate` first
  asks "is this licence already bound?" and, since it was, compared server and
  player id, found both different, and stopped with "bound to a different game
  account". The signed main-castle coordinates are only compared on the *first*
  binding of a licence, so that check was never reached.
* There was no way out. `licence_state` was a singleton row (`CHECK (singleton = 1)`)
  and `save_licence` upserted on it, so pasting another token would have
  **replaced** Ventrilo's licence, not added one.

## Why the coordinates were still a question

A licence is issued per account (`--server`, `--bootstrap-x`, `--bootstrap-y` are
signed into the token) and binds to the player id the first time that account
logs in with matching server and main castle. So a licence for Pingpoko needs
Pingpoko's server and main-castle coordinates, which nobody had written down:

* `owned_castle` has no Pingpoko row, because the licence check runs on the
  `gbd` packet *before* the bootstrap is stored.
* The refused `gbd` was not recorded either (the error returns first).

So the only way to learn the coordinates was to log in again, and the app threw them
away. That is fixed (below).

## Also found: Ventrilo's licence expires today

`ventrilo-stage0` expires 8 Oct 09:27:05 (about 7,000 s left when checked at 07:30). It
is the four-day token. Renew it before then, with the same `--license-id`, a higher
`--revision`, and a later expiry; see `admin/licence_admin.md`.

## Fixed (API v44, schema V20)

* **One licence per game account.** New `licence` table keyed by `license_id`
  (the old singleton is copied across and no longer used). Adding a token with a new
  `license_id` adds a licence; the same `license_id` with a higher revision renews
  it. Others are never touched. A unique index on `licence_activation (server,
  player_id)` stops one account being bound by two licences.
* **The licence is chosen when the account logs in**, not when the app starts:
  1. a licence already bound to this (server, player) is used;
  2. otherwise an unbound licence whose signed server **and** main castle match
     this account is bound to it, permanently;
  3. otherwise the login is refused with
     `no licence for this game account: server WORLD2, player N, main castle (X, Y)`.
* **The identity is kept.** On case 3 an `event_log` row `licence.needed` stores the
  server, player id and main castle, so the coordinates to have a licence issued for
  are in the database and in the window's status, not lost.
* **Each session is checked against its own licence** every 5 s. A second account's
  licence expiring no longer stops the first, and the other way round.
* **The window** accepts a token for another account through the same "Add credits /
  update plan" box, and afterwards says which account it is waiting for (server and
  main castle). `/v1/licence` now also returns `licences[]` with each licence's
  state, the server and castle it was issued for, and what it is bound to.

## What to do for a new account

1. Connect the account once. It is refused, and the window shows its server, player
   id and main castle (also in `event_log`, kind `licence.needed`):

   ```sql
   SELECT datetime(at_ms/1000,'unixepoch','localtime'), detail
   FROM event_log WHERE kind = 'licence.needed' ORDER BY id DESC LIMIT 5;
   ```
2. Issue a licence for exactly that server and castle (`admin/licence_admin.md`).
3. Paste it in "Add credits / update plan", then connect the account again.

## Not changed

* A licence is still permanent for one account once bound; there is no unbinding.
  Moving a licence to another account means issuing a new one.
* The main castle is only compared at first binding, so an account that later moves
  its main castle keeps its licence (this is intentional and tested).

## Follow-up: the app opened straight in on Ventrilo's licence

The window only shows the token screen when **no** licence is valid. Ventrilo's was
valid, so the app opened directly into the dashboard and nothing ever asked for
Pingpoko's token; the only route was the small "OpenAuto plan" button in the header,
easy to miss. (No password is stored or replayed anywhere; "auto login" was the
licence check passing, not a connection.)

The build that was installed at the time was **API 43** (`/v1/health` reported it
after the fix was written for 44). On that build the licence store is still the
single-row table, so pasting Pingpoko's token there would have **replaced**
Ventrilo's licence rather than added to it. Do not paste a second account's token
into a pre-44 build.

Fixed in the window:

* A login that no installed licence covers now opens the **Add a licence** panel by
  itself, with the refusal text (server, player id, main castle). It shows once per
  distinct refusal, so it cannot nag.
* The same panel (header **OpenAuto plan** button) lists every installed licence:
  who it is for, what server and main castle it was issued for, whether it is bound
  (and to which player) or still waiting, and when it expires.

## Install order

1. Build and install a release with API 44 or later (`/v1/health` shows
   `"api_version":44`). On first start it copies the existing licence into the new
   table.
2. Paste `admin/ventrilo-stage0-30-day.token` (renewal, revision 2).
3. Paste `admin/pingpoko-stage0-30-day.token`. The list now shows it waiting for the
   WORLD2 account at 552:522.
4. Connect Pingpoko. It binds on that login.
