# Problem 19: no login, 404s and database errors: a stale service on the port, and a game socket that must offer compression

Two separate faults showed up as one: the window said "request failed 404", showed database-looking errors, and signing in did nothing.

## Result

After the stale daemon was replaced by the rebuilt one, **signing in worked**: the account `pingpoko` connected (`phase: sands_ready`, bot pacing and acknowledging attacks) through the rebuilt standalone daemon
(API 55, with `empire-socket`). The installed window stayed on the old 0.1.70 build; it only talks to the daemon, which is what opens the game socket.

**Was it just the version number?** Partly unknowable, and worth keeping straight, because both changes landed together:

* `CLIENT_VERSION` was bumped `1170022` to `1171008` the session before (problem 17). The server hangs up on a version it no longer accepts, so a stale version *is* a real way for login to fail.
* But the version is only sent *after* the socket is open (`verChk`, then `vck` later). The `400 Bad Request` in Fault B happens at the HTTP upgrade, before any version is sent, so **a wrong version number cannot cause that 400**. A client that does not offer compression
  never reaches the point where the version matters.
* What was **not** tested: the new transport with the *old* version `1170022`. That would show whether the bump alone was enough once the socket opened. It was not tried because a wrong-version login risks the account's login lock (`login.locked_until_ms`, status 27).
  So: version bump = necessary-looking and done; compression offer = proven necessary; neither is proven sufficient alone.

### When logins stop working again: what to check first, cheapest first

| Check | Command | If it fails, it is... |
| --- | --- | --- |
| Which service holds the port, and is it current | `curl -s 127.0.0.1:47821/v1/health`: `api_version` equals `API_VERSION` in `crates/empire-daemon/src/lib.rs` | a stale service (Fault A): 404s, database errors, nothing logs in |
| Does the socket open and answer | `cargo run -p empire-socket --example verchk` | `400` or no `101`: the upgrade shape changed (Fault B, headers or compression). `101` but no `apiOK`: the server is refusing the session at the transport level |
| Is the version still accepted | compare `CLIENT_VERSION` (`empire-core/src/session.rs`) with the `vck` the live web client sends (record it with `proxy_packet_monitor` "Record full handshake") | `apiOK` arrives but the socket is closed right after `vck`: the version moved |
| Credentials / token | the account's status in the window | the server answered `lli` with an error status, not a transport problem |

The first two need no account and no login, so they never risk a lock. Do the third from a capture, not by trying versions on the live account.

## Fault A (service): an old `empire-daemon` held port 47821

**What was seen.** OpenAuto 0.1.70 (API 55) was installed and open, but `GET /v1/health` on `127.0.0.1:47821` answered `"api_version":17`. The process was
`rust_distributable/target/release/empire-daemon`, a build from 2026-10-04, started from the process-monitor panel's `github_gge_bot` entry (that entry
runs `./target/release/empire-daemon`). Every route the current window calls that did not exist in version 17 returned an empty `404`:
`/v1/overview`, `/v1/troops`, `/v1/transfers`, `/v1/dev`, `/v1/chat`, `/v1/pvp`, `/v1/direct/all`, `/v1/station/jobs`.
The database (`com.openauto.desktop/empire.sqlite3`, schema 27, integrity ok) belongs to the new code; the old process reading and writing it
is the source of the database errors. The database itself was not damaged.

**Why the app did not fix it.** On start the window already checks `/v1/health` for the API version it was built with and replaces an incompatible
service. But it may only stop a process it can *prove* is its own, and the check recognised only `empire-desktop --service`. The standalone
`empire-daemon` binary did not match, so the app logged "could not identify the incompatible OpenAuto service" (to nowhere: the window has no stderr) and
carried on against the old API.

**Fix.**
* `desktop/src-tauri/src/main.rs`: `is_our_service` also accepts a process whose program file name is `empire-daemon`; three tests cover it (the window itself is never matched).
* `target/release/empire-daemon` was rebuilt, so the panel's entry now runs the same code as the app.
* The stale process was stopped and the rebuilt daemon started; `/v1/health` reports `api_version 55` and every route above answers 200.

**How to tell next time.** `curl -s 127.0.0.1:47821/v1/health`: its `api_version` must equal `API_VERSION` in `crates/empire-daemon/src/lib.rs`. If not, whatever
holds the port is older than the window; quit it (or reopen the window, which now replaces a stale `empire-daemon` itself).

## Fault B (packets): the game server answers `400 Bad Request` to an upgrade that does not offer compression

**What was seen** (live, 2026-10-21, `ep-live-world2-game.goodgamestudios.com`, raw HTTP upgrade requests):

| Upgrade request | Answer |
| --- | --- |
| no `Sec-WebSocket-Extensions`, any `Origin` (new, old, none) | **`400 Bad Request`**, empty body |
| `Sec-WebSocket-Extensions: permessage-deflate` (with or without `client_max_window_bits`), any `Origin`, with or without `User-Agent` | `101`, extension echoed |
| `x-webkit-deflate-frame` | `101`, extension echoed |

So the **Origin was not the blocker** (the server answers the same for any); a deflate extension is. Problem 17's headers were harmless but not the fix, and
17's note that compression "was not shown to be required" is now answered: it is. After the upgrade the server sends its messages **compressed** (RSV1, raw
deflate, as *binary* frames); `tungstenite` rejects RSV1, so it could not have read even the first reply (`apiOK`). What the client sends can stay
uncompressed: a plain `verChk` text frame is accepted and answered.

**Fix.** A new crate, `crates/empire-socket`, is the one place that opens the game socket (the layer rule: `empire-core` must not open sockets):
* `game_request(url)` builds the upgrade request with every browser header **including the `permessage-deflate` offer** (`empire-core/src/ws_handshake.rs` keeps the values);
* it does the TLS itself and wraps the byte stream in `InflatingStream`, which passes the upgrade response through, then reads the server's frames, inflates the compressed
  messages (the deflate window carries over between messages) and hands `tokio-tungstenite` ordinary frames, so every caller keeps using `Message` and `split()` unchanged;
* callers: the daemon's session (`direct/mod.rs`) and relay, `empire-login`, `empire-hunt`.
* Tests (11): framing, fragmentation, a ping between fragments, one-byte-at-a-time delivery, masked frames, corrupt and oversized input, and a whole in-memory exchange against a
  fake server that insists on the offer and sends compressed messages.
* **Live check** (no credentials): `cargo run -p empire-socket --example verchk` gives `HTTP 101`, `permessage-deflate` and the decompressed `apiOK`.

Also fixed on the way: `empire-core::transfer` needs the optional `empire_game` crate but was compiled without the `application` feature, so `empire-core` (and `empire-login`, which turns
default features off) did not build; `transfer` is now behind `application` like its neighbours.

## Not verified / left alone

* **The credentialed login was run by the owner, not in this session's tests.** Our own live check stops at `apiOK`; the daemon then logged `pingpoko` in and it is running (see Result). Whether the server *requires*
  the browser's `RCT` token in `lli` (problem 17 saw one in every browser `lli`) was not needed here: the token login (`LT`) succeeded without one.
* **The installed app (0.1.70) is still the old build.** Signing in works because the *daemon* opens the game socket and the window only talks to the daemon. The running daemon is the stand-alone `target/release/empire-daemon`
  (rebuilt); a new app build is needed to ship `empire-socket` and `is_our_service` inside the app itself. Until then, do not start an older stand-alone `empire-daemon` on the port (the app would not have
  replaced it before this fix, and a binary built before `empire-socket` cannot sign in at all).
* **`server_no_context_takeover` / `client_max_window_bits` replies** are not parsed: the server answers plain `permessage-deflate`, and keeping the receive window for the whole connection is correct either way.
* **The probe script `probe_pingpoko_ws.py`** (project root) already offered compression; it was not changed.
