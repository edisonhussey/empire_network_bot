# Problem 17: the game moved its page and the client version, and our WebSocket upgrade no longer looked like the page's

> **Partly superseded by [problem 19](19.md).** The Origin and headers below are harmless and stay, but a live check showed the server's real requirement is a **`permessage-deflate` offer** (a socket without it gets `400`, whatever the Origin), which `empire-socket` now provides.

## The problem (packets)

Logins over the direct WebSocket stopped working after the game's update. The frame order did not change: the live
captures of 2026-10-18 and 2026-10-21 (`proxy_packet_monitor`) both run `verChk, apiOK, login, nfo, rlu, autoJoin,
joinOK, roundTrip + vck, lli`. What did change:

* **Client version.** (A wrong version cannot cause the socket-level `400` of [problem 19](19.md): it is sent only after the socket is open.) `1170022` became `1171008`; the server now answers `vck` with `6.1177.2 / 43.0.0` (was `6.1174.6 / 42.3.0`), data version `788.02`.
* **The page's Origin.** The browser now opens the socket from `https://empire-html5.goodgamestudios.com`; the client sent
  `https://empire.goodgamestudios.com` (still correct only inside `lli` `REF`). A wrong Origin is answered with HTTP 101
  and then silence, so it looks like a dead socket rather than a refusal.
* **The upgrade request itself.** It had only `Origin`. Chrome sends `User-Agent`, `Accept-Language`, `Pragma`, `Cache-Control` and
  `Sec-WebSocket-Extensions: permessage-deflate; client_max_window_bits`; the server answers `permessage-deflate`.
  The only cookies were consent and analytics ones, so no game session cookie is involved.

Seen with the new **Record full handshake** option of `proxy_packet_monitor` (upgrade headers, TLS and the requests just before the socket are stored with the LOGIN event).

## The fix

* `empire-core::ws_handshake` holds the page Origin and the browser's upgrade headers in one place (`UPGRADE_HEADERS`). The direct session
  (`empire-daemon/src/direct/mod.rs`) and the login proof (`empire-login`) insert every pair on the request before connecting.
* `CLIENT_VERSION` is `1171008`.
* Tests: the header names and values are valid for `HeaderName::from_static` / `HeaderValue`, and the Origin pair is first.

## Not verified / left alone

* **Nothing here was run against the live server** (the build environment cannot reach the game). The Origin change is the
  likeliest cause of the silent socket, from the docs' own earlier finding that a wrong Origin gets 101 and no `apiOK`.
* **`permessage-deflate` is not offered.** `tungstenite` 0.29 has no deflate feature and rejects frames with the RSV1 bit, so offering it would need a different
  WebSocket library. The capture shows the server *accepts* compression when asked; it does not show the server *requires* it. Do not swap the library until a live attempt shows the server refusing an uncompressed socket.
* **`lli` still needs `RCT` for the browser.** Every browser `lli` seen (2026-10-18 and 2026-10-21) carries a ~2.6k-character `RCT` that looks like a reCAPTCHA token (the page calls Google reCAPTCHA just before login).
  The client only sends one when the user supplies `registration_token`; it is not generated here.
* The portal flow also sends `vln` (and on 2026-10-18 `vpn`) before `lli`; the pingpoko token login sends neither.
